# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SexyInterrupter is a World of Warcraft addon (pure Lua + WoW XML, no build step, no package.json). It tracks which group/raid members can interrupt spell casts, shares that state between players via addon comm messages, and shows an on-screen prompt ("Interrupt now!") to whoever is next in the interrupt rotation.

There is no compiler, linter, or test suite in this repo — it is deployed by copying/symlinking the addon folder into the WoW `Interface/AddOns/` directory and reloading the game (`/reload`) or restarting the client. Verify changes by loading the addon in-game.

## Packaging / CI

- `.github/workflows/package.yml` runs `BigWigsMods/packager` on every push to `master`, publishing to CurseForge/WoWInterface/GitHub via `CF_API_KEY`, `WOWI_API_TOKEN`, `GITHUB_OAUTH`.
- `.github/workflows/release.yml` runs the same packager on tag pushes matching `*.*.*` (not pre-release tags like `*.*.*-*`).
- The addon's interface version(s) and release version live in [SexyInterrupter.toc](SexyInterrupter.toc) (`## Interface:`, `## Version:`). Bump `## Version` for releases; `SI.Version` in [settings.lua](settings.lua) reads it via `C_AddOns.GetAddOnMetadata`/`GetAddOnMetadata` (see below).
- **Single unified `.toc`, not per-flavor files.** `## Interface: 120100, 16001` covers current retail (12.1.0, per [github.com/Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source)'s `live` branch — re-check that repo for the current number before releasing) and **World of Warcraft: Forever** (beta Interface `16001`, client flavor codename `Camelot`, installs under a `_classic_beta_` folder — it's built on the Classic client line, not modern Retail, despite exposing the newer `Settings.RegisterCanvasLayoutCategory` options-panel API, confirmed by testing). This repo briefly used a separate `SexyInterrupter_Camelot.toc` (Blizzard's per-flavor-suffix convention, e.g. `_Vanilla.toc`/`_Wrath.toc`) before consolidating to one file with a comma-separated `## Interface` list — confirmed as the current real-world approach by checking BigWigs' live `BigWigs.toc` (`## Interface: 11508, 11509, 16001, 20505, 20506, 30405, 38002, 40402, 50503, 50504, 120100, 120105, 120007`). Prefer adding more comma-separated interface numbers over reintroducing per-flavor `.toc` files.
- **Evoker was missing** from `SI.interruptSpells`/`SI.unitCanInterrupt` in [settings.lua](settings.lua) (the class didn't exist when those tables were last touched) — added `351338` (Quell) and `evoker = { damager = true }` (Devastation/Augmentation have it; Preservation doesn't) for retail parity. If other specs/talents grant additional interrupts later, they go in the same two tables.

## Architecture

Load order is defined in [SexyInterrupter.toc](SexyInterrupter.toc): locale files first, then `core.lua → version.lua → settings.lua → events.lua → utils.lua → communication.lua → ui.lua → SexyInterrupter.xml`. Third-party Ace3/LibStub libraries are pulled in via [embeds.xml](embeds.xml) from `lib/`.

- **core.lua** — Addon bootstrap via AceAddon. `OnInitialize` sets up saved variables, options UI, the on-screen frames, and registers events/comm. `SI_Globals` (account-wide) holds the live roster of known interrupters (`SI_Globals.interrupters`); `formatVersion` gates a wipe/migration when the saved-data shape changes.
- **[old_events.lua](old_events.lua) is not loaded by any `.toc` file** — it's a superseded, orphaned earlier version of `events.lua` (its `COMBAT_LOG_EVENT_UNFILTERED`/`GROUP_ROSTER_UPDATE` predate the current `events.lua`). Don't mistake it for live code; `git blame`/diff it against `events.lua` if you need history on how a handler evolved, but edit `events.lua`, not this file. One real regression from that refactor: the old `GROUP_ROSTER_UPDATE` called `SexyInterrupter:UpdateInterrupterSettings()` (rebuilds the Options → Assignments → Priority assignment tab) and the new one didn't — fixed by re-adding that call to `events.lua`'s `GROUP_ROSTER_UPDATE` and `communication.lua`'s `ReceiveUserInformation`. (Also note: that tab's `priority` group is intentionally `hidden` via `not IsInGroup()` — it's expected to show nothing while solo.)
- **events.lua** — WoW event handlers (`COMBAT_LOG_EVENT_UNFILTERED`, `UNIT_SPELLCAST_*`, `GROUP_ROSTER_UPDATE`, `PLAYER_REGEN_*`, etc.). This is where interrupt casts are detected (`SPELL_CAST_SUCCESS` against `SI.interruptSpells`), cooldowns are computed and locally applied, and the "can this unit interrupt" / role / priority bookkeeping happens per roster update.
  - **`COMBAT_LOG_EVENT_UNFILTERED` is currently dead code — but likely a Forever-beta-specific bug, not a documented/permanent restriction.** On the World of Warcraft: Forever beta client, `RegisterEvent("COMBAT_LOG_EVENT_UNFILTERED")` triggers "`<AddOn>` has been blocked from an action only available to the Blizzard UI" immediately at login, with **no accompanying Lua error/stack trace** — found by bisecting every call in `OnInitialize`/`RegisterEvents` one at a time down to this single line. This is commented out in [core.lua](core.lua)'s `RegisterEvents()`; `SexyInterrupter:COMBAT_LOG_EVENT_UNFILTERED()` in this file still exists but never runs, so the combat-log-based interrupt-cooldown detection (`SPELL_CAST_SUCCESS`/`SPELL_INTERRUPT` parsing) is dead. **Important:** don't assume this is a general, already-solved Blizzard restriction — retail's `Blizzard_APIDocumentationGenerated/CombatLogDocumentation.lua` has flagged this event `HasRestrictions = true` since patch 12.0.0 (Jan 2026), yet BigWigs' current live code (`Core/BossPrototype.lua`) still calls `RegisterEvent("COMBAT_LOG_EVENT_UNFILTERED")` successfully via the exact same mechanism AceEvent-3.0 uses internally. So the flag doesn't mean "registration is forbidden" in general; what we hit is most plausibly a bug/over-restriction specific to this very-new Forever beta build (which may not have had any boss-mod-style addon actually exercise this path yet, since Forever's dungeon content is itself brand new). Re-test whether `RegisterEvent("COMBAT_LOG_EVENT_UNFILTERED")` still blocks before assuming it's permanently unusable — Blizzard may simply fix the beta.
  - **Automatic detection is restored via `UNIT_SPELLCAST_SUCCEEDED` instead of the combat log.** `SexyInterrupter:UNIT_SPELLCAST_SUCCEEDED(...)` in [events.lua](events.lua) mirrors the old `SPELL_CAST_SUCCESS` branch (cooldown math, Shadowpriest talent adjustment, `SendInterrupt` broadcast), but is fed by `UNIT_SPELLCAST_SUCCEEDED` (registered broadly in `core.lua`'s `RegisterEvents()`, filtered by unit name in the handler — same pattern as the other `UNIT_SPELLCAST_*` handlers) instead of `COMBAT_LOG_EVENT_UNFILTERED`. This event is **not** part of the restricted combat-log event family; per Blizzard's own generated docs (`UnitDocumentation.lua`), its `spellID` payload field is only turned into an unreadable "secret value" `SecretWhenUnitSpellCastRestricted` (e.g. rated PvP) — for normal group/dungeon content it's a plain number. Verify this still works after any client update; if `spellID` ever comes through as a secret value in your content, `tContains(self.interruptSpells, spellID)` will just silently never match (no error) and this'll need `issecretvalue()`-style guards.
  - **`SexyInterrupter:MarkOwnInterrupt()`** ([events.lua](events.lua)) is a manual backstop/self-serve alternative, triggered via the `/si kick` slash command (see `settings.lua`'s slash handler). Scans `SI.interruptSpells` for one currently on cooldown via `GetSpellCooldown`/`C_Spell.GetSpellCooldown` and broadcasts it through the same `SendInterrupt`/`ReceiveInterrupt` comm path, for when automatic detection misses something (e.g. a secret-value `spellID`) or for players who prefer a manual confirm. A keybinding (`Bindings.xml`) was attempted for this but dropped — this Forever beta client rejects any `<Binding>` XML element ("Unrecognized XML: Binding") regardless of exact attribute casing/schema tried (matched against Blizzard's own `Blizzard_PingUI/Bindings.xml`), suggesting Classic-derived beta builds don't support addon keybinding registration the same way retail does. Re-test if picking this back up.
- **communication.lua** — Cross-client sync over `AceComm`/`AceSerializer` using a single addon prefix (`SexyInterrupter`) and a `prefix` field inside the serialized payload to route messages (`versioninfo`, `requestuser`, `userinfos`, `interrupt`). Channel is chosen based on instance/group type (`INSTANCE_CHAT`/`RAID`/`PARTY`). This is the source of truth for keeping every client's `SI_Globals.interrupters` roster consistent.
- **utils.lua** — Shared helpers: interrupter lookup/creation (`GetInterrupter`, `UpdateInterrupters`), sort order for who's up next (`GetCurrentInterrupters`, sorted by offline/in-range/dead/readyTime/priority), on-screen warning flasher frames, frame lock/drag/anchor persistence, and the interrupt-now notification (text/sound/screen flash).
- **ui.lua** — `CreateUi()` builds the anchor frame, message frame, and right-click menu; `UpdateUI()`/`UpdateInterrupterStatus()`/`OnUpdate()` render the per-row status bars (see "Key data model" below for what a row now represents).
- **settings.lua** — Static data tables (`SI.interruptSpells` spell IDs, `SI.unitCanInterrupt` per class+role, output channels, anchor positions), AceConfig options table, and defaults for the AceDB profile (`self.db.profile.*`: general, notification, ui sections) driving the in-game config panel.
- **version.lua** — `SexyInterrupter.versions`: changelog entries shown via LibNotify on update.
- **locale/** — `AceLocale-3.0` string tables (`enUS.lua`, `deDE.lua`); add new user-facing strings to both.
- **lib/** — Vendored Ace3 / LibStub / LibSharedMedia / LibDataBroker / LibDBIcon / LibNotify libraries; treat as third-party, don't hand-edit unless updating a vendored lib deliberately.
  - The core Ace3 libraries (AceAddon-3.0, AceComm-3.0, AceConsole-3.0, AceDB-3.0, AceDBOptions-3.0, AceEvent-3.0, AceGUI-3.0, AceConfigDialog-3.0, AceConfigRegistry-3.0, AceHook-3.0, AceLocale-3.0, AceSerializer-3.0, AceTimer-3.0, CallbackHandler-1.0, LibStub) were bulk-replaced with a fresh pull from the official upstream repo, [github.com/WoWUIDev/Ace3](https://github.com/WoWUIDev/Ace3) (`master` branch). That repo shipped an explicit `AceDB-3.0: Compatibility with WoW Forever` commit within days of the Forever beta launching, and current `AceGUI-3.0` no longer calls the removed global `SetDesaturation`. This superseded an earlier attempt at bulk-copying from Questie's bundled libs (`.../AddOns/Questie/Libs/`), which were already stale by comparison. To refresh: shallow-clone the repo and copy each matching top-level folder over `lib/<name>`, plus `AceConfig-3.0/AceConfigDialog-3.0` → `lib/AceConfigDialog-3.0` and `AceConfig-3.0/AceConfigRegistry-3.0` → `lib/AceConfigRegistry-3.0` (this repo keeps those two as standalone folders per `embeds.xml`, not nested under `AceConfig-3.0`). `LibSharedMedia-3.0`, `LibDataBroker-1.1`, `LibDBIcon-1.0`, `AceGUI-3.0-SharedMediaWidgets` (not part of core Ace3) and `LibNotify-1.0` (no upstream equivalent) are unaffected by this and still come from Questie/this repo's original vendoring.
  - `SI.Version` in [settings.lua](settings.lua) resolves via `C_AddOns.GetAddOnMetadata` first, falling back to the legacy global `GetAddOnMetadata`, then to a hardcoded `"3"` — the Forever beta client has neither metadata API reliably available, and this call runs at file-load time (before any function body), so any unguarded failure here aborts the rest of `settings.lua`'s load, silently breaking `InitOptions`/`OnInitialize` (no options panel, no `/si`, no on-screen UI). Keep the fallback in sync with `## Version` in the `.toc` files.
  - **lib/LibUIDropDownMenu/** (vendored from Questie's `LibUIDropDownMenuQuestie-4.0`) replaces Blizzard's native `"UIDropDownMenuTemplate"` for the right-click menu. Since WoW 11.0, addon-created frames using that template are hard-blocked ("`<AddOn>` has been blocked from an action only available to the Blizzard UI"), and Forever inherits this restriction. [ui.lua](ui.lua)'s `CreateUi()` builds `SexyInterrupterMenu` via `LibDD:Create_UIDropDownMenu(...)` instead of `CreateFrame(..., "UIDropDownMenuTemplate")`, and [utils.lua](utils.lua)'s `OnMouseUp` calls `LibDD:EasyMenu(...)` instead of the global `EasyMenu(...)`. Note `SexyInterrupter.menu` (the right-click menu's contents) is never actually defined anywhere in this codebase — the menu has always been empty/a stub; `OnMouseUp` guards this with `SexyInterrupter.menu or {}` to avoid crashing on the nil menu list rather than fixing the underlying (pre-existing, out-of-scope) missing feature.
  - The vendored `AceGUI-3.0`'s "Dropdown" widget type ([lib/AceGUI-3.0/widgets/AceGUIWidget-DropDown.lua](lib/AceGUI-3.0/widgets/AceGUIWidget-DropDown.lua)) *also* creates a `"UIDropDownMenuTemplate"` frame internally, and upstream Ace3 hasn't fixed this widget yet (unlike `AceDB-3.0`/`AceGUI-3.0`'s `SetDesaturation` removal). Rewriting that widget to route through `LibUIDropDownMenu` would be a large, invasive change (it also uses many native `UIDropDownMenu_*` globals beyond frame creation), so instead this repo avoids the widget entirely: any AceConfig `type = "select"` option must use `style = "radio"`, never `style = "dropdown"` (or no `style`, which also defaults to the Dropdown widget) — see the three `outputchannel`/`point`/`relativePoint` fields in [settings.lua](settings.lua). This does **not** apply to the `LSM30_*` (font/sound/statusbar/background/border) dialog controls from `AceGUI-3.0-SharedMediaWidgets` — those build their own frames without a template and are unaffected.

### Key data model

Each entry in `SI_Globals.interrupters` (an array, looked up by `fullname`/`name` via `GetInterrupter`) is one **player**, tracking: `name`/`realm`/`fullname`, `class`/`classEN`/`classColor`, `role` (TANK/HEALER/DAMAGER), `prio` (derived from role, or `overridedprio`), `canInterrupt` (derived from `SI.unitCanInterrupt[class][role]`), `active`, `offline`/`afk`/`dead`/`inrange`.

**Multi-ability tracking (per player, dynamically learned):** a player's individual interrupt abilities are *not* predetermined from a class/spec table — they're discovered live as `UNIT_SPELLCAST_SUCCEEDED` (events.lua) sees that player successfully cast something in `SI.interruptSpells`. Each discovered ability is stored in `interrupter.abilities[spellId] = { cooldown, readyTime }`, keyed by spell ID, so a player with e.g. two interrupts (talent/covenant granting a second one, or a class like Death Knight with both Mind Freeze and Strangulate) accumulates multiple entries independently. `interrupter.cooldown`/`interrupter.readyTime` (top-level, no `abilities` prefix) still exist as a **derived aggregate**: after every `GetCurrentInterrupters()` call, they're overwritten to mirror that player's single best (soonest-ready) ability, for the handful of call sites that only care about "is this player generally ready" (`ShowInterruptWarning` in utils.lua, the fallback row when nobody's up next) rather than which specific ability.

`SexyInterrupter:GetCurrentInterrupters()` (utils.lua) returns **one row per (player, known ability) pair**, not one row per player — a player with 2 abilities produces 2 sorted rows, each with its own `spellId`/`cooldown`/`readyTime` and a `.interrupter` back-reference to the shared player object for name/role/class/offline/etc. A player with no ability discovered yet still gets a single placeholder row (`spellId = nil`) so they don't vanish from the rotation before their first known kick. Rows are sorted globally by the same offline → in-range → alive → readyTime → priority rule as before, just operating on row-level `readyTime` instead of player-level. `ui.lua`'s `UpdateInterrupterStatus()` renders one bar per row, showing that ability's own spell icon (`C_Spell.GetSpellTexture`/`GetSpellTexture`) when `spellId` is known, falling back to the role icon otherwise.

Because `GetCurrentInterrupters()` now yields multiple rows per player, any code that wants **one entry per player** (the priority-assignment settings tab in `settings.lua`'s `UpdateInterrupterSettings`/`SendOverridePrioInfos`) must de-duplicate on `row.interrupter` first — see those two functions for the pattern (a `seen[interrupter] = true` set keyed by table identity).

The `interrupt` comm message (communication.lua's `SendInterrupt`/`ReceiveInterrupt`) now carries `spellId` alongside `cooldown`, so a broadcast updates the correct specific ability in the receiver's `interrupter.abilities` table, not a single player-wide value.

`SI.interruptSpells` (settings.lua) remains required even with dynamic per-player learning — it's the master filter that answers "was this cast an interrupt at all" for `UNIT_SPELLCAST_SUCCEEDED`/`MarkOwnInterrupt`, since that event fires for every successful spell cast, not just interrupts. `SI.unitCanInterrupt` is a separate table (class+role → can this unit ever interrupt) used for roster-level filtering, independent of which specific ability they've been seen using. When adding a new class/spec interrupt ability: add the spell ID to `SI.interruptSpells` and the class/role capability to `SI.unitCanInterrupt`, both in [settings.lua](settings.lua).

### Edit Mode settings & persistence (EditModeExpanded-1.0)

- **All user-facing options except the priority-assignment tab live in the Edit Mode dialogs** (`RegisterEditModeSettings` in [ui.lua](ui.lua)), including width, output channel and the sound file. AceConfig only keeps the "Open Edit Mode" button, the assignments tab and the profiles tab — don't add a group with zero visible children (AceGUI TabGroup divides by zero).
- **AceDB is the single source of truth.** The library keeps its own per-Edit-Mode-layout copy of every checkbox/slider value and re-runs the callbacks on every profile refresh. Our callbacks therefore only write to AceDB while `EditModeExpandedSystemSettingsDialog` is shown (a real click); otherwise they `Resync()` the library's value from AceDB. Every frame's `SelectSystem` is wrapped to resync before its dialog is built (the library shows 100 for a missing slider value).
- **Position storage:** after its first profile init the library moves `x/y/settings` out of the table we pass to `RegisterFrame` into a nested per-layout table. Always read/write positions via `GetLiveDB(frame, fallback)` (= `EME.framesDB[frame.system]`), never via `editModeAnchorDB.x/y` directly.
- `notification.soundFile` may hold an LSM sound *name* or a raw path — always resolve through `SexyInterrupter:ResolveSoundPath`.
- The (always empty) right-click menu was removed: no `OnMouseUp` handlers, no `SexyInterrupterMenu`, `SexyInterrupter:OnMouseUp` is gone. `LibUIDropDownMenu` is now only used for the Edit Mode dropdowns (font/texture/sound/output channel/grow direction) — ignore the older bullet above that describes the right-click menu.
